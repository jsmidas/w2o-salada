# W2O SALADA 배송 코스 설계

> 2026-09-26 작성. 배송지를 구역으로 묶고 차량에 고정 배정하는 새벽배송 코스 체계.
> 오픈 전 검토용 — 현장(다함푸드 배송 담당)과 합의가 필요한 항목은 마지막 절에 모았다.

---

## 왜 지금 필요한가

지금은 **어느 집을 누가 가는지 정할 근거가 시스템에 없다.**

`Delivery.driverId`를 코스 라벨로 재사용해서, 관리자가 `/admin/delivery`에서
**주문 한 건마다 코스명을 손으로 타이핑**하는 게 전부다. 배송 20건까지는 되지만
200건에서는 불가능하다. 더 근본적인 문제는 묶을 근거가 없다는 것이다.

### 주소에 위치 정보가 없다

`Address`는 `address1` 문자열 하나만 들고 있다. "강남구끼리 묶기"조차
문자열을 파싱해야 하고, 아파트인지 단독주택인지 알 수 없다.

그런데 **이미 쓰고 있는 다음 우편번호 API가 필요한 값을 전부 준다.**

| API 응답 필드 | 값 예시 | 현재 처리 |
|---|---|---|
| `sido` / `sigungu` / `bname` | 서울 / 강남구 / 역삼동 | 버림 |
| `buildingName` | 래미안그레이튼 | `address1` 문자열에 합침 |
| `apartment` | `"Y"` / `"N"` | **버림** |

```ts
// apps/web/app/checkout/page.tsx — 현재
const addr = data.buildingName ? `${data.address} (${data.buildingName})` : data.address;
setAddress({ address1: addr, zipCode: data.zonecode });
```

저장만 하면 되는 값이라 **추가 API도 비용도 0원**이다. 좌표는 별도로
카카오 로컬 API가 필요하지만(무료 한도 일 30만 건), 행정동 + 단지명만으로도
코스 설계의 대부분이 가능하다. 지도는 그다음 문제다.

### 배송 가능 지역 검증이 없다

FAQ에는 "서울 전 지역, 인천 일부, 경기 주요 신도시"라고 쓰여 있지만
코드에 검증이 없다. 지금은 제주도 주소로도 결제가 된다. 주문을 받은 뒤
취소·환불로 처리하는 비용이 그대로 발생한다.

## 실무 원칙

### 1. 용량은 "건수"가 아니라 "스톱"으로 잰다

아파트 단지 12건은 엘리베이터 한 번이라 사실상 1~2스톱이고,
단독주택 1건은 주차 + 도보로 온전한 1스톱이다. 소요 시간이 비슷하다.

"차량당 80건"으로 배정하면 **아파트 코스는 놀고 가정집 코스는 터진다.**
용량은 두 축으로 잡는다.

- `maxStops` — 차량 한 대가 도는 정차 지점 수
- `maxBoxes` — 적재 한계

스톱 수 계산: 같은 `buildingName`의 주문은 1스톱으로 묶고, 나머지는 건당 1스톱.

### 2. 새벽배송은 고정 코스가 정석이다

매일 최적 경로를 다시 푸는 방식은 새벽배송에 맞지 않는다.
00~06시 안에 끝내는 걸 좌우하는 건 알고리즘이 아니라 **기사의 숙련도**다
— 공동현관 비밀번호, 주차 위치, 엘리베이터 대기 패턴, 어느 동이 먼저인지.

구역을 코스에 **고정 배정**하고, 일별로는 물량만 확인해 초과분만 손으로
넘기는 방식으로 간다. 경로 최적화(TSP)는 코스가 5개를 넘고 나서 검토한다.

### 3. 아파트 타겟은 전략적으로 옳다

단지 1곳에 10건이면 건당 배송원가가 단독주택의 1/5~1/10이다.
그래서 확장의 단위를 **"지역"이 아니라 "단지"**로 잡는다.

- 신규 단지 오픈 기준 — 사전 신청 N건 이상 모이면 배송 개시
- 단지별 최소 유지 건수 — 미달 시 배송비 부과 또는 중단 협의
- 단독주택·사업장은 기존 코스 **경로상에 있을 때만** 수용

이 판단을 하려면 단지별 주문 수 집계가 필요하고, 그러려면
`buildingName`이 별도 컬럼에 있어야 한다.

## 데이터 모델

### Address — 위치 정보 추가

```prisma
model Address {
  // ... 기존 필드 유지
  sido         String?   // 서울
  sigungu      String?   // 강남구
  bname        String?   // 역삼동 (법정동)
  buildingName String?   // 래미안그레이튼 — 단지 단위 묶음의 키
  isApartment  Boolean @default(false) // 다음 API의 apartment === "Y"
  lat          Float?    // 2단계
  lng          Float?    // 2단계
  zoneId       String?   // 배송 구역 (자동 매칭 결과를 캐시)
  zone         DeliveryZone? @relation(fields: [zoneId], references: [id])

  @@index([sigungu, bname])
  @@index([buildingName])
}
```

`buildingName`은 **단지 묶음의 키**다. 표기 흔들림(래미안그레이튼 / 래미안 그레이튼)이
생기면 묶이지 않으므로, 다음 API가 준 값을 **가공 없이** 저장한다.
주소 문자열에 합치는 현재 방식은 버린다.

### DeliveryZone — 배송 구역

코스의 재료. 행정동 또는 단지 단위로 정의한다.

```prisma
model DeliveryZone {
  id          String   @id @default(cuid())
  name        String   // "강남-역삼"
  matchType   ZoneMatchType  // DONG | BUILDING
  matchValues String[] // ["역삼동","도곡동"] 또는 ["래미안그레이튼"]
  routeId     String?  // 기본 배정 코스
  route       DeliveryRoute? @relation(fields: [routeId], references: [id])
  isActive    Boolean  @default(true)
  addresses   Address[]
}

enum ZoneMatchType { DONG BUILDING }
```

`BUILDING`이 `DONG`보다 우선한다. 같은 동이라도 큰 단지는 독립 구역으로
떼어내야 하는 경우가 생긴다(단지 하나가 코스 하나를 채우는 상황).

### DeliveryRoute — 코스 = 차량 1대의 하루

```prisma
model DeliveryRoute {
  id          String   @id @default(cuid())
  name        String   // "A코스"
  ownership   RouteOwnership @default(OWN) // 자차/용차 — 배정 순서를 가른다
  driverName  String?  // 기사 (Phase 4에서 User 연결로 전환)
  vehicleNo   String?  // 차량번호
  maxStops    Int  @default(100) // 집 수 기준 (현장 운영 목표)
  maxBoxes    Int  @default(200) // 적재 확인용 보조 지표
  departTime  String?  // "02:00" — 코스별 시차 출발
  departOrder Int  @default(0) // 출고 순서 — 상차 순번
  isActive    Boolean @default(true)
  zones       DeliveryZone[]
}

enum RouteOwnership { OWN OUTSOURCED }
```

### Delivery — 코스 참조를 정식 필드로

```prisma
model Delivery {
  // ... 기존 필드
  routeId   String?        // driverId 재사용을 끝내고 정식 FK로
  route     DeliveryRoute? @relation(fields: [routeId], references: [id])
  stopOrder Int @default(0) // 코스 내 방문 순번 (기존 sortOrder 대체)
}
```

현재 `driverId`에 코스 라벨 문자열을 넣는 임시 방편을 정리한다.
마이그레이션 시 기존 `driverId` 값은 `DeliveryRoute`로 승격시킨다.

### 배정 규칙

```
주소 → (1) buildingName이 BUILDING 구역과 일치하는가?
      → (2) bname이 DONG 구역에 포함되는가?
      → (3) 어디에도 안 걸리면 "미배정" 큐로
```

(3)이 중요하다. **신규 지역 주문을 조용히 아무 코스에나 넣으면 안 된다.**
미배정 큐에 쌓아두고 관리자가 판단하게 한다 — 구역을 새로 열지,
기존 코스에 흡수할지, 배송 불가로 안내할지.

## 운영 플로우

```
PM 11:00  주문 마감
   ↓      주소 → 구역 → 코스 자동 배정
   ↓      코스별 스톱/박스 집계, 용량 초과 경고, 미배정 큐 표시
PM 11:20  관리자가 초과분·미배정만 손봄 (전체를 손대지 않는다)
PM 11:30  배송 리스트 확정 (PAID → PREPARING)
   ↓      코스별 배송지시서 출력 (A4/A3 — 생산 집계와 동일 방식)
AM 02:00  코스 순서대로 상차 (departOrder)
AM 03:00  배송 출발
```

핵심은 **관리자가 전체를 배정하지 않는다**는 점이다.
자동 배정이 90%를 처리하고, 사람은 예외만 본다.

### 배송 가능 지역 검증

주문 단계에서 막는다. 결제 후 취소는 비용이다.

- 구역에 매칭되지 않는 주소 → 결제 진행 차단 + "배송 예정 지역" 안내
- 사전 알림 신청을 받아두면 신규 단지 오픈 판단 근거가 된다
  (단지별 신청자 수가 곧 오픈 기준 N건)

## 화면 설계

### `/admin/delivery-routes` — 코스 마스터 (신규)

코스와 구역을 관리한다. 자주 바뀌지 않는 설정 화면.

- 코스 목록: 이름, 기사, 차량, 최대 스톱/박스, 출고 순서
- 코스별 구역 편집: 행정동/단지를 붙였다 뗐다
- 구역 미할당 목록: 주문은 들어오는데 구역이 없는 동/단지

### `/admin/delivery` — 코스 편성 (기존 개선)

배송일마다 보는 화면. 지금은 주문마다 코스명을 타이핑하는데,
자동 배정 결과를 검토하는 화면으로 바꾼다.

- 상단: 코스별 현황 카드 — `A코스 42/60 스톱 · 88/120 박스` (초과 시 빨강)
- 좌측: 미배정 큐 (신규 지역 주문)
- 본문: 코스별 그룹, 단지 단위로 묶여서 표시
- 조작: 드래그로 코스 간 이동, 단지째 통으로 이동
- 출력: 코스별 배송지시서

### `/admin/delivery-map` — 지도 (3단계)

좌표가 쌓인 뒤. 코스별 색상 핀, 미배정 주소 강조.
**단지 침투율**(단지별 주문 수)을 함께 보여주면 영업 판단에 쓸 수 있다.

## 단계별 로드맵

| 단계 | 범위 | 하는 일 | 시점 |
|---|---|---|---|
| **1** | 주소 + 좌표 | 다음 API 필드 저장, 카카오 지오코딩, **반경 판정**, 경계 밖 HOLD 처리, 아파트 단지 사전 등록 | **오픈 전** |
| 2 | 구역·코스 | 코스 마스터, 자동 배정, 코스 추가 경고, 코스별 배송지시서 | 물량 50집 |
| 3 | 지도 | 코스별 시각화, 단지 침투율, 대기 수요 분포 | 코스 2개 |
| 4 | 최적화 | 코스 내 방문 순서, 기사 앱 연동 | 나중에 |

### 1단계를 오픈 전에 해야 하는 이유

두 가지다.

**주소는 다시 받을 수 없다.** 고객이 한 번 입력하면 건드리지 않으므로,
지금 안 받으면 쌓인 주소를 소급 보정해야 한다. 문자열에서 단지명을
역파싱하는 건 정확도가 떨어진다. 배송지가 아직 1건인 지금이 가장 싸다.

**좌표 없이는 주문을 받을지조차 판정할 수 없다.** 배송 가능 기준이
행정구역이 아니라 센터 반경이기 때문이다. 초안에서는 좌표를 2단계로
미뤘으나, 현장 기준이 "반경 5km"로 확인되면서 1단계 필수로 올렸다.

2단계 이후는 물량이 늘 때 해도 늦지 않다. 오픈 초기 규모면 코스
1개로 충분하고, 그 정도는 지금의 수동 입력으로도 돌아간다.

| 차량 | 자차 + 직영 용차, 수요에 맞춰 증차 자유 |
| 배송 단위 | **한 집 = 1건** (샐러드·반찬·오니기리 여러 개여도 1건) |
| 차량당 목표 | 100집 (운영 기준) |

| 배송 시간 | 03:00 출발, 4시간 내 완료 |
| 생산 방식 | **2~3일 전 발주 → 전날 저녁 조리·포장 완료 → 냉장보관 → 새벽 배송** |
| 보관 가능 | 샐러드 3~4일(토핑 조절), 오니기리 2~3일, 반찬도시락 장기 |
| 배송 지역 | 대구 달서구 + **센터 반경 5km 내 달성군**. 대구 밖 미진출 |
| 물류센터 | 1센터 대구 달서구 성서공단로 332-10 / 2센터(예정) 경북 경산 영남지사 |
| 배송비 | **무료** (본품 11,000원 이상 주문 조건) |
| 신규 단지 기준 | **1건이라도 수용**, 단 기존 코스에서 원거리가 아닐 것 |
| 경계 밖 주문 | 차단하지 않고 접수 → 주간(08~17시) 직접 전화로 취소 또는 대기 안내 |
| 최소 유지 건수 | 도입기라 판단 보류 |

### 배송 단위가 "집"이라는 점의 의미

현장 기준이 "한 집 = 1건"이므로, 이 문서의 **스톱 = 집**으로 통일한다.
같은 주소에 샐러드 2개 + 반찬 1개가 가도 1스톱이다. 따라서
`maxStops`는 **주소 수**로 세고, `maxBoxes`는 적재 확인용 보조 지표가 된다.

같은 아파트 단지의 서로 다른 세대는 **각각 1스톱**이되, 이동 비용이
거의 없으므로 실질 소요는 훨씬 짧다. 그래서 단지 밀집 코스는
100집을 넘겨도 무리가 없고, 단독주택 코스는 100집도 벅차다.
자동 배정에서 **단지 집중도**를 함께 보여줘야 하는 이유다.

```
코스 용량 판정 = 주소 수, 그리고 그중 아파트 비중
  A코스  92집 / 아파트 88%  → 여유 (단지 위주)
  B코스  78집 / 아파트 21%  → 포화 (단독주택 산재)
```

### 코스 정산 구조와 "분기점"

용차는 **최소비용 보장 용역**이다. 코스 하나의 정산액은 이렇게 정해진다.

```
코스 정산액 = max(보장액, 집수 × 건당단가)
            = max(100,000원, 집수 × 1,000원)     ← 현재 가정
```

가까운 코스를 50집만 돌든, 먼 코스를 200집 돌든 기사가 손해 보지 않게
하는 구조다. 여기서 **분기점**이 나온다.

```
분기점 = 보장액 ÷ 건당단가 = 100,000 ÷ 1,000 = 100집
        (보장액이 7만 원이면 70집)
```

| 코스에 실은 집 | 정산액 | 건당 원가 |
|---|---|---|
| 50집 | 100,000원 (보장) | 2,000원 |
| 80집 | 100,000원 (보장) | 1,250원 |
| **100집** | **100,000원** | **1,000원** ← 분기점 |
| 150집 | 150,000원 | 1,000원 |
| 200집 | 200,000원 | 1,000원 |

### 여기서 나오는 운영 규칙

**분기점을 넘긴 코스는 몇 집을 더 실어도 건당 원가가 1,000원으로
평평하다.** 이 사실이 코스 분할 판단을 뒤집는다.

```
300집을 나누는 경우
  1코스 300집 → 300,000원 (건당 1,000원)  기사 부담 과중
  2코스 150집 → 300,000원 (건당 1,000원)  동일
  3코스 100집 → 300,000원 (건당 1,000원)  동일 ← 가장 여유롭다
  4코스  75집 → 400,000원 (건당 1,333원)  보장액 차액 발생
```

즉 **각 코스가 분기점(100집) 이상이기만 하면 코스를 몇 개로 나누든
총비용이 같다.** 그렇다면 기사 부담과 오류 위험을 줄이는 쪽이 낫다.
"한 차량에 너무 많이 실으면 오류가 난다"는 현장 우려가
**원가 손해 없이 해소된다.**

### 자동 배정 규칙

```
분기점   = 보장액 / 건당단가                 (설정값, 기본 100집)
물리한계 = 기사 1명이 4시간에 도는 최대 집수  (설정값, 기본 200집)

코스 수 = clamp(
  floor(총 집수 / 분기점),     ← 이보다 많이 나누면 보장액 차액 발생
  ceil(총 집수 / 물리한계),    ← 이보다 적으면 시간 내 불가
  최소 1
)
→ 구역 단위로 균등 분배
```

보장액·건당단가·물리한계는 `Setting`에 두어 관리자가 조정한다
(보장액이 7만 원으로 바뀌면 분기점이 70집으로 자동 반영).

자차는 고정비 구조라 별도로 본다. 자차가 있으면 **자차 코스를 먼저
채운 뒤** 남는 물량에 위 계산을 적용한다.
`DeliveryRoute.ownership`(OWN | OUTSOURCED)으로 구분한다.

코스를 분기점 미만으로 열어야 할 때(물량 부족, 지리적 고립)는
**관리자에게 원가 영향을 보여준 뒤 결정하게 한다.**
"C코스를 75집으로 열면 보장액 차액 25,000원이 발생합니다."

### 배송 가능 지역 — 행정구역이 아니라 "센터 반경"이 기준이다

현장 기준은 행정구역이 아니다. **성서공단로 332-10 기준 반경 5km**이고,
달성군이라 해서 다사읍·현풍·구지 전체를 여는 개념이 아니다.

이 때문에 판정 방식이 바뀐다.

- 행정동 화이트리스트만으로는 **같은 동 안에서 가깝고 먼 곳을 못 가른다**
- 반경 판정을 하려면 **주소 좌표가 필수**다
- 따라서 **좌표 수집이 2단계가 아니라 1단계로 올라간다**

```
배송 가능 판정
  1) 주소 → 좌표 (카카오 로컬 API)
  2) 센터 좌표와의 거리 계산
  3) 반경 이내 → 자동 수용
     반경 초과 → 보류(HOLD), 주간에 전화 확인
```

행정동 화이트리스트는 **보조 수단**으로 남긴다. 좌표를 못 얻은 주소나
반경 경계에 걸친 지역을 수동으로 열고 닫을 때 쓴다.

반경은 `Setting`에 값으로 두어 관리자가 조정할 수 있게 한다
(초기 5km → 물량이 늘면 확대). 2센터(경산) 가동 시에는 센터가 둘이므로
**가장 가까운 센터 기준**으로 판정하고, 그 센터의 코스에 배정한다.

### 경계 밖 주문은 차단하지 않는다

배송지는 개별 판단이 필요한 경우가 많다는 현장 의견에 따라,
**결제를 막지 않고 접수한 뒤 주간에 사람이 판단**한다.

```
반경 초과 주문 접수 → 주문 상태 HOLD, 관리자 큐에 표시
  → 08:00~17:00 사이 담당자가 고객에게 전화
    → 취소 처리, 또는
    → "해당 지역에 코스가 생길 때까지 대기" 안내 후 대기 명단 등록
```

대기 명단이 쌓이면 **지역별 대기 수요**가 보여서 신규 코스 개설
판단 근거가 된다. 단지별로 집계하면 "이 단지 8명 대기 → 코스 연장"
같은 판단이 가능하다.

## 미해결 쟁점

설계를 확정하기 전에 판단이 필요한 항목.

### 0. 주문 마감 시점이 실제 생산과 맞지 않는다 — 최우선

**CLAUDE.md의 배송 사이클이 실제 운영과 다르다.**

```
문서: PM 11:00 주문 마감 → AM 12:00 조리 시작 → AM 03:00 출발
실제: 2~3일 전 발주 → 전날 저녁 조리·포장 완료 → 냉장보관 → 새벽 배송
```

현장 지적대로 **전날 23시 마감으로는 물량을 맞출 수 없고, 재료·조리
손실이 크다.** 재료 발주가 2~3일 전에 이뤄지므로, 주문 마감도 그에
맞춰 앞당겨져야 한다.

이건 배송 코스보다 우선순위가 높다. 마감 시각이 정해져야
[생산 집계](../apps/web/app/admin/production)가 **발주용 수량**을
언제 확정해 뽑을지 정할 수 있다.

→ **확인 필요**
  - 재료 발주 마감을 D-2로 잡는가, D-3으로 잡는가?
  - 그 시점에 주문을 마감하면 구독 고객의 메뉴 변경은 언제까지 허용하는가?
    (구독은 `SubscriptionSelection`으로 미리 선택되니 문제가 적지만,
     단건 주문과 메뉴 변경분을 어떻게 처리할지 정해야 한다)
  - 마감 이후 들어온 주문은 **다음 배송일로 넘기는가**, 여유분으로 받는가?

이 답이 나오면 CLAUDE.md의 배송 사이클과 주문 마감 로직을 함께 고친다.

### 1. 기사 1명의 물리 한계를 얼마로 볼 것인가

분기점(100집) 이상이면 코스를 나눠도 원가가 같으므로, **코스 분할은
원가가 아니라 기사가 감당 가능한 집수로 결정된다.** 그래서 이 숫자가
자동 배정의 실질 기준이 된다.

- 4시간에 200집이면 **집당 1.2분** — 아파트 단지 위주여야 가능
- 100집이면 집당 2.4분 — 단독주택이 섞여도 무난

→ **확인 필요**
  - 물리 한계를 단일 값(200집)으로 둘 것인가, **아파트 비중에 따라
    달리** 볼 것인가? (예: 단지 80% 이상이면 200집, 50% 미만이면 120집)
  - 초기에는 보수적으로 잡고 실적을 쌓아 조정하는 방식이 안전하다.
    실제 배송 소요 시간을 기록해두면 이 값을 데이터로 보정할 수 있다.

### 2. 손익 모델 반영 (완료) — 보장액은 서둘러 확정할 필요가 없다

손익분기 시뮬레이터(`tools/build_breakeven_model.py`)의 배송비를
건당 3,500원 고정에서 `max(코스수 × 보장액, 집수 × 단가)` 구조로
바꿨다. 결과는 아래와 같다 (객단가 18,000원, 고정비 월 2,000만 원 가정).

| 배송일당 집수 | 코스 | 건당 배송비 | 건당 공헌이익 | 월 영업이익 |
|---|---|---|---|---|
| 40집 | 1 | 2,500원 | 6,484원 | −17,746,162원 |
| 80집 | 1 | 1,250원 | 7,734원 | −14,623,323원 |
| 100집 | 1 | 1,000원 | 7,984원 | −13,061,904원 |
| 200집 | 1 | 1,000원 | 7,984원 | −6,123,808원 |
| 300집 | 2 | 1,000원 | 7,984원 | **+814,288원** |

```
손익분기 배송일당 집수
  보장액 10만 원 → 289집
  보장액  7만 원 → 289집   ← 같다
  (기존 3,500원 고정 가정이었다면 420집)
```

**보장액 7만 원과 10만 원의 손익분기점이 같다.** BEP 지점(289집)에서는
이미 분기점을 한참 넘어 건당 원가가 단가(1,000원)로 수렴하기 때문이다.
보장액이 실제로 영향을 주는 구간은 **분기점 미만의 초기 저물량**뿐이고,
그 차이도 배송일당 40집에서 월 26만 원, 80집에서 월 17만 원 수준이다.

따라서 **보장액은 지금 확정하지 않아도 된다.** 협상에서 유리한 쪽으로
가져가되, 시뮬레이터의 가정값 셀로 두고 필요할 때 바꾼다.
"보장액별 실질 건당 배송비" 비교표를 손익분기 시트에 넣어두었다.

같은 이유로 **코스당 최대 집수(물리 한계)도 원가에는 영향이 없다.**
분기점 이상 물량에서는 코스를 몇 개로 나누든 총액이 같기 때문이다.
이 값은 원가가 아니라 **배송 품질과 기사 부담**을 정하는 숫자다.

### BEP를 지배하는 건 배송비가 아니라 고정비다

배송비를 현실화해도 BEP는 여전히 높다. 실제로 BEP를 움직이는 건
고정비이고, **월 100만 원을 줄일 때마다 BEP가 약 14~15집 내려간다.**
시뮬레이터에 "시나리오" 시트를 추가해 규모별로 비교할 수 있게 했다.

| 시나리오 | 월 고정비 | BEP | 월 주문 |
|---|---|---|---|
| A. 안정기 | 1,900만 원 | 274집 | 2,381건 |
| B. 축소 운영 | 950만 원 | 137집 | 1,191건 |
| C. 최소 시작 (모회사 공유) | 550만 원 | **82집** | 713건 |

274집과 82집은 사실상 다른 사업이다. 82집이면 **아파트 단지 3~4곳**
수준이라 오픈 초기에 도달 가능한 범위에 들어온다.

고정비를 낮추는 실질적인 방법은 **고정비를 변동비로 바꾸는 것**이고,
W2O는 이미 그 방향에 있다.

- **배송 차량** — 자차 대신 용차. 월 고정비가 건당 변동비가 된다
  (시뮬레이터의 "차량·냉장설비" 항목에서 차량분을 분리해 제거했다)
- **주방** — 모회사(다함푸드) 주방 공유 시 별도 임대료가 사라진다
- **인력** — 초기 전담 4~5명은 무겁다. 겸업·파트타임으로 시작해
  물량에 맞춰 늘린다

다만 **위생·품질 관리와 최소 인력은 줄이지 않는다.** 새벽배송은
냉장 유지가 생명이고, 2~3일 보관 후 배송하는 구조라 더 그렇다.
포장 오류나 배송 누락은 단지 내 입소문으로 빠르게 번진다.

→ 남은 확인
  - 어느 시나리오로 시작할 것인가? 모회사와 공유 가능한 자원
    (주방, 인력, 창고)의 범위가 정해지면 C안의 현실성이 확정된다.
  - 자차를 운용한다면 1대의 월 고정비(기사 인건비 + 차량)는 얼마인가?
    자차·용차 분기점 계산에 필요하다.

### 3. 달서구도 반경 기준인가

손익분기 시뮬레이터(`tools/build_breakeven_model.py`)는 건당 위탁
배송비를 **3,500원**으로 잡고 있다. 현장 판단은 **1,000원**이다.
**3.5배 차이**이고, 건당 변동비 전체를 흔드는 규모라 손익분기점이
크게 달라진다. 둘 중 하나는 고쳐야 한다.

건당 1,000원이 성립하려면 기사 1명이 **하루 150~200집**을 돌아
일당 15~20만 원이 나와야 한다. 물리 한계 200집과는 맞아떨어지지만,
**오픈 초기 물량(배송일당 수십 건)에서는 성립하지 않는다.**
80집이면 기사 수입이 8만 원이라 새벽 시간대에 사람을 구하기 어렵다.

현실적인 형태는 **코스당 최소 보장 + 초과분 건당 정산**이다.
예: 1코스 최소 12만 원 보장, 120집 초과분은 건당 1,000원.
이 경우 초기에는 **실질 건당 단가가 1,500~2,000원**까지 올라가므로,
손익 모델도 물량 구간별로 나눠 잡아야 한다.

→ 확인 필요: 용차 업체와 실제 협의된 조건이 건당 1,000원 단순 정산인가,
  최소 보장이 붙는가? 자차 1대의 월 고정비(기사 인건비 + 차량)는 얼마인가?

센터 반경 5km가 기준이라면 **달서구도 전 지역이 아니다.**
달서구는 남북으로 길어서, 성서산업단지에서 상인동·월배 방면은
8~10km로 5km를 넘는다.

| 방면 | 센터에서 | 반경 5km |
|---|---|---|
| 이곡·신당·용산 | 1~3km | 포함 |
| 죽전·감삼·본리 | 3~5km | 경계 |
| 상인·월배·도원 | 8~10km | **초과** |
| 달성군 다사읍 동부(죽곡 등) | 2~4km | 포함 |

→ **확인 필요**: 달서구는 구 전체를 여는가, 아니면 달서구도 반경
  5km로 자르는가? 전자라면 "달서구 전역 + 달성군 반경 5km",
  후자라면 "행정구역 무관, 센터 반경 5km"로 규칙이 단순해진다.

개인적으로는 **후자(반경 단일 규칙)**를 권한다. 규칙이 하나라 설명하기
쉽고, 2센터(경산)가 열릴 때도 같은 규칙이 그대로 적용된다. 상인·월배는
물량이 모이면 반경을 8km로 넓히거나 별도 코스로 여는 방식으로 대응한다.

### 4. 아파트 단지 사전 등록 (도입 확정)

공공데이터포털의 **공동주택 단지 정보**로 대상 지역 단지 목록을
미리 적재한다. 단지명·주소·세대수·동수가 들어온다.

활용처는 셋이다.

1. **주소 입력 시 단지 자동 매칭** — `buildingName` 표기 흔들림을
   사전 등록된 단지명으로 보정해 묶음 정확도를 높인다
2. **영업 우선순위** — 세대수가 곧 잠재 수요다. 센터에서 가깝고
   세대수가 많은 단지부터 공략한다
3. **침투율 지표** — 단지별 (주문 수 / 세대 수)를 보면
   어느 단지가 살아나는지, 어디에 전단을 돌릴지 판단할 수 있다

```prisma
model Apartment {
  id          String  @id @default(cuid())
  name        String  // 단지명 (공공데이터 기준 표기)
  aliases     String[] // 표기 흔들림 보정용
  address     String
  sigungu     String
  bname       String
  households  Int?    // 세대수
  lat         Float?
  lng         Float?
  distanceKm  Float?  // 센터에서의 거리 (캐시)
  isServiced  Boolean @default(false) // 배송 개시 여부
  zoneId      String?
}
```

## 결정 기록

- **고정 코스 우선, 동적 최적화는 보류** — 새벽배송에서는 기사 숙련도가
  경로 계산보다 실질 소요를 좌우한다. 코스 5개를 넘기 전까지는
  최적화 알고리즘을 넣지 않는다.
- **좌표는 1단계 필수** — 배송 가능 판정이 센터 반경 기준이므로
  좌표 없이는 주문 수용 여부조차 가릴 수 없다.
  (초안에서는 2단계로 미뤘으나 현장 기준 확인 후 뒤집었다)
- **분기점 이상이면 코스를 나눠도 원가가 같다** — 용차가 최소비용
  보장 용역(`max(보장액, 집수 × 단가)`)이라, 코스당 분기점(보장액 ÷
  단가 = 100집)을 넘기면 건당 원가가 평평해진다. 따라서 코스 분할은
  원가가 아니라 기사 부담으로 결정하고, **분기점 미만으로 코스를 열 때만**
  관리자에게 차액을 보여주고 확인받는다.
- **경계 밖 주문은 막지 않고 보류한다** — 배송지는 개별 판단이 필요한
  경우가 많다는 현장 의견에 따라, 접수 후 주간에 사람이 전화로 판단한다.
- **`buildingName`은 가공 없이 저장** — 표기가 흔들리면 단지 묶음이
  깨진다. 정규화가 필요하면 별도 매핑 테이블을 두되, 원본은 보존한다.
- **미배정은 조용히 흡수하지 않는다** — 신규 지역 주문을 자동으로
  아무 코스에 넣으면 현장에서 사고가 난다. 큐에 쌓고 사람이 판단한다.
- **스톱 = 집** — 현장 기준을 그대로 따른다. 한 주소에 몇 개가 가든 1스톱.
- **자차를 먼저 채우고 용차로 넘긴다** — 자차는 고정비, 용차는 건당
  변동비라 자차를 놀리면서 용차에 지불하는 건 순손실이다.
- **코스별 시차 출발로 조리 시간을 확보한다** — 마감을 앞당기거나
  전처리를 전날로 미루는 대신, 먼 코스부터 포장해 순차 출발시킨다.
