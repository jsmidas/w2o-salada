# W2O SALADA 배송 코스 설계

> 2026-09-26 작성. 배송지를 구역으로 묶고 차량에 고정 배정하는 새벽배송 코스 체계.
> 오픈 전 검토용 — 현장(다함푸드 배송 담당)과 합의가 필요한 항목은 마지막 절에 모았다.

## 왜 지금 필요한가

지금은 **어느 집을 누가 가는지 정할 근거가 시스템에 없다.**

`Delivery.driverId`를 코스 라벨로 재사용해서, 관리자가 `/admin/delivery`에서
**주문 한 건마다 코스명을 손으로 타이핑**하는 게 전부다. 배송 20건까지는 되지만
200건에서는 불가능하다. 더 근본적인 문제는 묶을 근거가 없다는 것이다.

### 주소에 위치 정보가 없다

`Address`는 `address1` 문자열 하나만 들고 있다. "강남구끼리 묶기"조차
문자열을 파싱해야 하고, 아파트인지 단독주택인지 알 수 없다.

그런데 **이미 쓰고 있는 다음 우편번호 API가 필요한 값을 전부 준다.**

| API 응답 필드 | 값 예시 | 현재 처리 |
|---|---|---|
| `sido` / `sigungu` / `bname` | 서울 / 강남구 / 역삼동 | 버림 |
| `buildingName` | 래미안그레이튼 | `address1` 문자열에 합침 |
| `apartment` | `"Y"` / `"N"` | **버림** |

```ts
// apps/web/app/checkout/page.tsx — 현재
const addr = data.buildingName ? `${data.address} (${data.buildingName})` : data.address;
setAddress({ address1: addr, zipCode: data.zonecode });
```

저장만 하면 되는 값이라 **추가 API도 비용도 0원**이다. 좌표는 별도로
카카오 로컬 API가 필요하지만(무료 한도 일 30만 건), 행정동 + 단지명만으로도
코스 설계의 대부분이 가능하다. 지도는 그다음 문제다.

### 배송 가능 지역 검증이 없다

FAQ에는 "서울 전 지역, 인천 일부, 경기 주요 신도시"라고 쓰여 있지만
코드에 검증이 없다. 지금은 제주도 주소로도 결제가 된다. 주문을 받은 뒤
취소·환불로 처리하는 비용이 그대로 발생한다.

## 실무 원칙

### 1. 용량은 "건수"가 아니라 "스톱"으로 잰다

아파트 단지 12건은 엘리베이터 한 번이라 사실상 1~2스톱이고,
단독주택 1건은 주차 + 도보로 온전한 1스톱이다. 소요 시간이 비슷하다.

"차량당 80건"으로 배정하면 **아파트 코스는 놀고 가정집 코스는 터진다.**
용량은 두 축으로 잡는다.

- `maxStops` — 차량 한 대가 도는 정차 지점 수
- `maxBoxes` — 적재 한계

스톱 수 계산: 같은 `buildingName`의 주문은 1스톱으로 묶고, 나머지는 건당 1스톱.

### 2. 새벽배송은 고정 코스가 정석이다

매일 최적 경로를 다시 푸는 방식은 새벽배송에 맞지 않는다.
00~06시 안에 끝내는 걸 좌우하는 건 알고리즘이 아니라 **기사의 숙련도**다
— 공동현관 비밀번호, 주차 위치, 엘리베이터 대기 패턴, 어느 동이 먼저인지.

구역을 코스에 **고정 배정**하고, 일별로는 물량만 확인해 초과분만 손으로
넘기는 방식으로 간다. 경로 최적화(TSP)는 코스가 5개를 넘고 나서 검토한다.

### 3. 아파트 타겟은 전략적으로 옳다

단지 1곳에 10건이면 건당 배송원가가 단독주택의 1/5~1/10이다.
그래서 확장의 단위를 **"지역"이 아니라 "단지"**로 잡는다.

- 신규 단지 오픈 기준 — 사전 신청 N건 이상 모이면 배송 개시
- 단지별 최소 유지 건수 — 미달 시 배송비 부과 또는 중단 협의
- 단독주택·사업장은 기존 코스 **경로상에 있을 때만** 수용

이 판단을 하려면 단지별 주문 수 집계가 필요하고, 그러려면
`buildingName`이 별도 컬럼에 있어야 한다.

## 데이터 모델

### Address — 위치 정보 추가

```prisma
model Address {
  // ... 기존 필드 유지
  sido         String?   // 서울
  sigungu      String?   // 강남구
  bname        String?   // 역삼동 (법정동)
  buildingName String?   // 래미안그레이튼 — 단지 단위 묶음의 키
  isApartment  Boolean @default(false) // 다음 API의 apartment === "Y"
  lat          Float?    // 2단계
  lng          Float?    // 2단계
  zoneId       String?   // 배송 구역 (자동 매칭 결과를 캐시)
  zone         DeliveryZone? @relation(fields: [zoneId], references: [id])

  @@index([sigungu, bname])
  @@index([buildingName])
}
```

`buildingName`은 **단지 묶음의 키**다. 표기 흔들림(래미안그레이튼 / 래미안 그레이튼)이
생기면 묶이지 않으므로, 다음 API가 준 값을 **가공 없이** 저장한다.
주소 문자열에 합치는 현재 방식은 버린다.

### DeliveryZone — 배송 구역

코스의 재료. 행정동 또는 단지 단위로 정의한다.

```prisma
model DeliveryZone {
  id          String   @id @default(cuid())
  name        String   // "강남-역삼"
  matchType   ZoneMatchType  // DONG | BUILDING
  matchValues String[] // ["역삼동","도곡동"] 또는 ["래미안그레이튼"]
  routeId     String?  // 기본 배정 코스
  route       DeliveryRoute? @relation(fields: [routeId], references: [id])
  isActive    Boolean  @default(true)
  addresses   Address[]
}

enum ZoneMatchType { DONG BUILDING }
```

`BUILDING`이 `DONG`보다 우선한다. 같은 동이라도 큰 단지는 독립 구역으로
떼어내야 하는 경우가 생긴다(단지 하나가 코스 하나를 채우는 상황).

### DeliveryRoute — 코스 = 차량 1대의 하루

```prisma
model DeliveryRoute {
  id          String   @id @default(cuid())
  name        String   // "A코스"
  ownership   RouteOwnership @default(OWN) // 자차/용차 — 배정 순서를 가른다
  driverName  String?  // 기사 (Phase 4에서 User 연결로 전환)
  vehicleNo   String?  // 차량번호
  maxStops    Int  @default(100) // 집 수 기준 (현장 운영 목표)
  maxBoxes    Int  @default(200) // 적재 확인용 보조 지표
  departTime  String?  // "02:00" — 코스별 시차 출발
  departOrder Int  @default(0) // 출고 순서 — 상차 순번
  isActive    Boolean @default(true)
  zones       DeliveryZone[]
}

enum RouteOwnership { OWN OUTSOURCED }
```

### Delivery — 코스 참조를 정식 필드로

```prisma
model Delivery {
  // ... 기존 필드
  routeId   String?        // driverId 재사용을 끝내고 정식 FK로
  route     DeliveryRoute? @relation(fields: [routeId], references: [id])
  stopOrder Int @default(0) // 코스 내 방문 순번 (기존 sortOrder 대체)
}
```

현재 `driverId`에 코스 라벨 문자열을 넣는 임시 방편을 정리한다.
마이그레이션 시 기존 `driverId` 값은 `DeliveryRoute`로 승격시킨다.

### 배정 규칙

```
주소 → (1) buildingName이 BUILDING 구역과 일치하는가?
      → (2) bname이 DONG 구역에 포함되는가?
      → (3) 어디에도 안 걸리면 "미배정" 큐로
```

(3)이 중요하다. **신규 지역 주문을 조용히 아무 코스에나 넣으면 안 된다.**
미배정 큐에 쌓아두고 관리자가 판단하게 한다 — 구역을 새로 열지,
기존 코스에 흡수할지, 배송 불가로 안내할지.

## 운영 플로우

```
PM 11:00  주문 마감
   ↓      주소 → 구역 → 코스 자동 배정
   ↓      코스별 스톱/박스 집계, 용량 초과 경고, 미배정 큐 표시
PM 11:20  관리자가 초과분·미배정만 손봄 (전체를 손대지 않는다)
PM 11:30  배송 리스트 확정 (PAID → PREPARING)
   ↓      코스별 배송지시서 출력 (A4/A3 — 생산 집계와 동일 방식)
AM 02:00  코스 순서대로 상차 (departOrder)
AM 03:00  배송 출발
```

핵심은 **관리자가 전체를 배정하지 않는다**는 점이다.
자동 배정이 90%를 처리하고, 사람은 예외만 본다.

### 배송 가능 지역 검증

주문 단계에서 막는다. 결제 후 취소는 비용이다.

- 구역에 매칭되지 않는 주소 → 결제 진행 차단 + "배송 예정 지역" 안내
- 사전 알림 신청을 받아두면 신규 단지 오픈 판단 근거가 된다
  (단지별 신청자 수가 곧 오픈 기준 N건)

## 화면 설계

### `/admin/delivery-routes` — 코스 마스터 (신규)

코스와 구역을 관리한다. 자주 바뀌지 않는 설정 화면.

- 코스 목록: 이름, 기사, 차량, 최대 스톱/박스, 출고 순서
- 코스별 구역 편집: 행정동/단지를 붙였다 뗐다
- 구역 미할당 목록: 주문은 들어오는데 구역이 없는 동/단지

### `/admin/delivery` — 코스 편성 (기존 개선)

배송일마다 보는 화면. 지금은 주문마다 코스명을 타이핑하는데,
자동 배정 결과를 검토하는 화면으로 바꾼다.

- 상단: 코스별 현황 카드 — `A코스 42/60 스톱 · 88/120 박스` (초과 시 빨강)
- 좌측: 미배정 큐 (신규 지역 주문)
- 본문: 코스별 그룹, 단지 단위로 묶여서 표시
- 조작: 드래그로 코스 간 이동, 단지째 통으로 이동
- 출력: 코스별 배송지시서

### `/admin/delivery-map` — 지도 (3단계)

좌표가 쌓인 뒤. 코스별 색상 핀, 미배정 주소 강조.
**단지 침투율**(단지별 주문 수)을 함께 보여주면 영업 판단에 쓸 수 있다.

## 단계별 로드맵

| 단계 | 범위 | 하는 일 | 시점 |
|---|---|---|---|
| **1** | 주소 데이터 | 다음 API 응답 필드 저장, 배송 가능 지역 검증 | **오픈 전** |
| 2 | 구역·코스 | 마스터 화면, 자동 배정, 용량 경고, 코스별 출력 | 물량 50건 |
| 3 | 좌표·지도 | 카카오 로컬 지오코딩, 지도 시각화, 단지 침투율 | 코스 3개 |
| 4 | 최적화 | 코스 내 방문 순서, 기사 앱 연동 | 나중에 |

### 1단계를 오픈 전에 해야 하는 이유

주소는 고객이 한 번 입력하면 다시 건드리지 않는다. 지금 안 받으면
쌓인 주소를 소급 보정해야 하는데, 문자열에서 단지명을 역파싱하는 건
정확도가 떨어진다. **배송지가 아직 1건인 지금이 가장 싼 시점**이고,
추가 비용도 0원이다.

2단계 이후는 물량이 늘 때 해도 늦지 않다. 오픈 초기 구독 43건 규모면
코스 1~2개로 충분하고, 그 정도는 지금의 수동 입력으로도 돌아간다.

## 확정된 운영 조건

> 2026-09-26 현장 답변 반영.

| 항목 | 값 |
|---|---|
| 차량 | 자차 + 용차 혼합, 수요에 맞춰 증차 자유 |
| 배송 단위 | **한 집 = 1건** (샐러드·반찬·오니기리 여러 개여도 1건) |
| 차량당 목표 | 100집 (운영 기준) |
| 기사 물리 한계 | 200집, 아파트 밀집이면 그 이상 |
| 용차 정산 | **건당 1,000원** (집 기준) |
| 배송 시작 | 현재 03:00, 물량 증가 시 02:00 또는 그 이전 |
| 배송 지역 | **대구 달서구 + 달성군**(현풍·구지 제외). 당분간 대구 밖 미진출 |
| 물류센터 | 1센터 대구 달서구 성서공단로 332-10 / 2센터(예정) 경북 경산 영남지사 |
| 신규 단지 기준 | **1건이라도 수용**, 단 기존 코스에서 원거리가 아닐 것 |
| 최소 유지 건수 | 도입기라 판단 보류 |

### 배송 단위가 "집"이라는 점의 의미

현장 기준이 "한 집 = 1건"이므로, 이 문서의 **스톱 = 집**으로 통일한다.
같은 주소에 샐러드 2개 + 반찬 1개가 가도 1스톱이다. 따라서
`maxStops`는 **주소 수**로 세고, `maxBoxes`는 적재 확인용 보조 지표가 된다.

같은 아파트 단지의 서로 다른 세대는 **각각 1스톱**이되, 이동 비용이
거의 없으므로 실질 소요는 훨씬 짧다. 그래서 단지 밀집 코스는
100집을 넘겨도 무리가 없고, 단독주택 코스는 100집도 벅차다.
자동 배정에서 **단지 집중도**를 함께 보여줘야 하는 이유다.

```
코스 용량 판정 = 주소 수, 그리고 그중 아파트 비중
  A코스  92집 / 아파트 88%  → 여유 (단지 위주)
  B코스  78집 / 아파트 21%  → 포화 (단독주택 산재)
```

### 자차 + 용차 혼합의 배정 순서

원가 구조가 다르므로 배정 순서가 손익을 가른다.

- **자차** — 고정비(기사 급여 + 차량 유지). 많이 실을수록 건당 원가가 내려간다
- **용차** — 건당 1,000원 변동비. 몇 건이든 건당 원가가 같다

따라서 **자차 코스를 먼저 채우고, 넘치는 물량만 용차로 넘긴다**
(fill-first). 자차를 놀리면서 용차에 건당 비용을 지불하는 건 순손실이다.
`DeliveryRoute`에 `ownership`(OWN | OUTSOURCED) 필드를 두고,
자동 배정은 OWN 코스를 용량까지 채운 뒤 OUTSOURCED로 넘긴다.

### 배송 가능 지역 화이트리스트

행정동 단위로 관리한다. 달서구는 전 지역, 달성군은 읍·면 단위로 연다.

- **달서구** — 전 행정동 (센터가 달서구 성서산업단지에 있어 접근성 최상)
- **달성군** — 다사읍·화원읍·옥포읍·논공읍 우선. 현풍읍·구지면 제외.
  **가창면·유가읍·하빈면은 거리 재검토 필요** (아래 미해결 쟁점 참고)

## 미해결 쟁점

설계를 확정하기 전에 판단이 필요한 항목.

### 1. 배송 단가 1,000원과 손익 모델 3,500원의 차이

손익분기 시뮬레이터(`tools/build_breakeven_model.py`)는 건당 위탁
배송비를 **3,500원**으로 잡고 있다. 현장 판단은 **1,000원**이다.
**3.5배 차이**이고, 건당 변동비 전체를 흔드는 규모라 손익분기점이
크게 달라진다. 둘 중 하나는 고쳐야 한다.

건당 1,000원이 성립하려면 기사 1명이 **하루 150~200집**을 돌아
일당 15~20만 원이 나와야 한다. 물리 한계 200집과는 맞아떨어지지만,
**오픈 초기 물량(배송일당 수십 건)에서는 성립하지 않는다.**
80집이면 기사 수입이 8만 원이라 새벽 시간대에 사람을 구하기 어렵다.

현실적인 형태는 **코스당 최소 보장 + 초과분 건당 정산**이다.
예: 1코스 최소 12만 원 보장, 120집 초과분은 건당 1,000원.
이 경우 초기에는 **실질 건당 단가가 1,500~2,000원**까지 올라가므로,
손익 모델도 물량 구간별로 나눠 잡아야 한다.

→ 확인 필요: 용차 업체와 실제 협의된 조건이 건당 1,000원 단순 정산인가,
  최소 보장이 붙는가? 자차 1대의 월 고정비(기사 인건비 + 차량)는 얼마인가?

### 2. 02:00 출발과 조리 시간의 충돌

현재 사이클(CLAUDE.md)은 이렇다.

```
PM 11:00  주문 마감
AM 12:00  조리/포장 시작
AM 02:00  포장 완료
AM 03:00  배송 출발
```

물량이 늘어 **02:00에 출발**하려면 포장이 01:00에 끝나야 하고,
조리 시간이 2시간에서 1시간으로 줄어든다. **물량이 늘어서 일찍
나가는 건데 조리 시간은 오히려 짧아지는** 모순이 생긴다.

선택지는 셋이다.

1. **주문 마감을 앞당긴다** (23:00 → 21:00) — 고객 편의가 줄어든다
2. **전처리를 전날로 당긴다** — 반찬·오니기리는 가능, 샐러드는 신선도상 부담
3. **코스별 시차 출발** — 먼 코스부터 포장해 02:00 출발,
   가까운 코스는 03:00 출발. `departOrder`가 이 용도다

3번이 가장 현실적이고 설계와도 맞는다. 다만 주방 작업이 코스 순서대로
진행돼야 하므로, 생산 집계와 피킹 리스트를 **코스별로 쪼개서 출력**하는
기능이 필요하다.

→ 확인 필요: 주방 캐파상 시간당 몇 집 분량을 포장할 수 있는가?
  이 숫자가 코스별 출발 시각과 마감 시각을 결정한다.

### 3. 달성군 원거리 읍·면

현풍·구지를 제외한 이유가 거리라면, **가창면·유가읍·하빈면도
같은 문제**를 안고 있다. 성서산업단지 센터 기준 대략 이렇다.

| 지역 | 센터에서 편도 | 판단 |
|---|---|---|
| 다사읍 | 약 5km | 무난 |
| 화원읍·옥포읍 | 10~12km | 무난 |
| 논공읍 | 약 15km | 가능 |
| 하빈면 | 약 15km, 농촌 산재 | 밀도 낮아 재검토 |
| 유가읍 | 25km 이상 | 사실상 현풍과 유사 |
| 가창면 | 30km 이상, 시내 관통 | **제외 권장** |

"1건이라도 배송"과 결합하면 가창면 1건에 왕복 60km를 가는 상황이
생긴다. 건당 1,000원으로는 감당이 안 되고, 용차 기사가 거부하거나
할증을 요구한다.

→ 확인 필요: 달성군을 읍·면 단위 화이트리스트로 시작해도 괜찮은가?
  (다사·화원·옥포·논공 우선, 나머지는 수요를 보고 추가)

### 4. 경계 밖 주문을 어떻게 받을 것인가

배송 불가 지역 주문을 **결제 단계에서 차단**하면 잠재 고객을 잃고,
**받아두면** 취소·환불 비용이 발생한다. 중간 형태로
"배송 예정 지역 알림 신청"을 받아두면 신규 지역 오픈 판단 근거
(지역별 대기 수요)가 쌓인다.

→ 확인 필요: 차단 + 알림 신청 형태로 갈 것인가?

## 결정 기록

- **고정 코스 우선, 동적 최적화는 보류** — 새벽배송에서는 기사 숙련도가
  경로 계산보다 실질 소요를 좌우한다. 코스 5개를 넘기 전까지는
  최적화 알고리즘을 넣지 않는다.
- **좌표보다 행정동·단지명이 먼저** — 지도는 보기 좋지만, 묶는 기준은
  행정동과 단지명으로 충분하다. 좌표는 시각화와 순서 최적화용이다.
- **`buildingName`은 가공 없이 저장** — 표기가 흔들리면 단지 묶음이
  깨진다. 정규화가 필요하면 별도 매핑 테이블을 두되, 원본은 보존한다.
- **미배정은 조용히 흡수하지 않는다** — 신규 지역 주문을 자동으로
  아무 코스에 넣으면 현장에서 사고가 난다. 큐에 쌓고 사람이 판단한다.
- **스톱 = 집** — 현장 기준을 그대로 따른다. 한 주소에 몇 개가 가든 1스톱.
- **자차를 먼저 채우고 용차로 넘긴다** — 자차는 고정비, 용차는 건당
  변동비라 자차를 놀리면서 용차에 지불하는 건 순손실이다.
- **코스별 시차 출발로 조리 시간을 확보한다** — 마감을 앞당기거나
  전처리를 전날로 미루는 대신, 먼 코스부터 포장해 순차 출발시킨다.
